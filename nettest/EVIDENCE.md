# M4 evidence – network tests on a real Linux laptop

Run on 2026-11-08 on a friend's laptop: Ubuntu 24.04.5 LTS, kernel 7.0.0-42, Python 3.12.3, iproute2-6.1.0 (`tc`),
Toxiproxy 2.9.0, code at commit `7c50be8`. Everything below comes from the files in this folder; nothing is
simulated. Steps followed: [RUNBOOK.md](RUNBOOK.md).

The lab is a private virtual cable (`vi-cli` ⇄ `vi-srv0`, server in its own network namespace). netem shapes both
directions (rate, delay, loss); Toxiproxy sits in front of the server to cut, reset or hang connections. Faults
fire when the client's own log shows it has reached a given fraction of the file, so every fault lands
mid-transfer whatever the link speed. Test video: 3,756,860 bytes, SHA-256 `7cb25b13…71b74739`, max chunk 512 KB.

| Strength | Rate | RTT | Loss (each direction) |
|---|---|---|---|
| 100% | 20 Mbit/s | 20 ms | 0% |
| 60% | 5 Mbit/s | 80 ms | 1% |
| 20% | 500 kbit/s | 400 ms | 5% |

## 3. Cross-checks on the raw logs

Done on `client.jsonl` (every chunk and retry) and `actions.jsonl` (every netem/Toxiproxy/kill action) of all 53
runs, independently of the harness's own summary:

- **Every byte is accounted for.** In every run the acknowledged chunks plus the server's resume offsets cover
  exactly 0 … 3,756,860. 13 runs show a jump in the client's chunk offsets; all 13 come right after a retry and
  are at most one chunk. Example (`interruption/rep1`): the chunk at 1,310,720 reached the server but the
  response was lost when the connection was cut; the client asked the server for its offset, got 1,835,008 and
  continued **without re-sending a chunk the server already had**.
- **Server crash (`server_restart`).** The client kept running and retried (4–5 times: `Server disconnected`,
  then `Connection reset` while the server was down) and continued at the server's verified offset
  (`rep1`: exactly 1,835,008). Extra bytes sent over the file size: at most one chunk (524,288; 496,608 in rep5).
  `resumed_bytes` is 0 here because that counter only counts resumes by a *new client process*.
- **Client crash (`client_restart`).** The new client process asked the server and resumed from 1.8–2.4 MB,
  so those bytes were not sent again.
- **Hung connections (`timeouts`).** Data silently dropped for 30 s, twice per run. The client's 20 s read
  timeout fired (`ReadTimeout`, 10 times over 5 runs) and it reconnected. The server marked the upload STALLED
  each time ("no chunk for 29.5–31.2 s") and RESUMED at the same offset when chunks came back.
- **What caused the retries**, by error: `ConnectError` (connection refused during interruption / network switch),
  `ReadError` (TCP reset), `RemoteProtocolError` (server vanished mid-response), `ReadTimeout` (hang). No retry
  was caused by anything else.

## 4. Findings, stated as found

- **The 20% link is slower than its 500 kbit/s cap.** stable_20 moved 3.76 MB in 152–217 s, about 140–200 kbit/s,
  and preflight measured 115 kbit/s. With 5% loss and 400 ms RTT, TCP backs off on every loss and cannot fill
  the line. This is a property of the emulated network, not of the uploader (no retries in those runs).
- **STALLED means "no completed chunk for 15 s" (the harness sets `VI_STALL_SECONDS=15`), not "broken".** In one
  stable_20 run with no fault (`rep3`) the first 256 KB chunk took longer than 15 s on the slow link and was marked
  STALLED, then RESUMED at offset 0. The state is computed when someone asks for it, so the recorded time is
  the first status read after 15 s of no progress, not the exact moment progress stopped.
- **2 of 50 server logs contain a `ClientDisconnect` traceback** (`resets/rep2`, `timeouts/rep1`): the connection
  was cut while a chunk body was still arriving. The server discarded the partial chunk before writing anything,
  the client re-sent it, and the hash matched. The behaviour is correct; only the logging is noisy (an
  uncaught exception instead of a one-line note). Not changed yet.
- `network_switch` keeps the client's IP address (the cable is the same); a real Wi-Fi → mobile switch also
  changes the address. The upload protocol does not depend on the client address, but this was not tested.

## Not verified

- A real mobile network or a real Wi-Fi → mobile handover (emulated only, see above).
- Larger files or a 30 s 1080p recording over the 20% link (one 3.76 MB test video).
- More than one machine: all 50 runs on one laptop, one kernel.
- The browser client under netem: M4 used the Python client. The browser client was tested against
  Toxiproxy resets and a server crash on Windows (M5 pytest), not against netem.
