What this log can prove

  • When each frame of the camera track reached the page during recording (captureTime, when the browser provides it), and the number of frames presented (presentedFrames).
  • Delivery gaps: periods in which no new frame reached the page. If the file has a gap at the same moment, the frames were most likely never delivered by the camera/OS, so they could not be recorded.
  • Regular delivery: if frames reached the page at a steady rate while the file has a gap, the frames were lost after capture, in the recording pipeline (MediaRecorder / encoder / muxer).
  • Whether the page was hidden (requestVideoFrameCallback pauses then) and how long recording ran.

What it cannot prove

  • What MediaRecorder actually encoded: the preview and the recorder are separate consumers of the track, so a frame shown in the preview may still be missing from the file (that is exactly the case the log helps to identify).
  • Why the camera did not deliver a frame (driver, USB bandwidth, exposure time, OS load): a delivery gap shows only that no frame arrived.
  • A frame that arrived but was replaced before display (page overloaded) looks the same as a delivery gap; it is told apart only if the file still contains that frame.
  • Exact times of frames presented without a callback (main thread busy): presentedFrames counts them, so they are known to have been delivered, but a short gap hidden among them could be missed.
  • Picture content: a camera that repeats or freezes a picture still delivers frames on time, so duplicated pictures cannot be attributed with this log.
  • Alignment: page clock and file timestamps are aligned by searching the offset at which file frames and logged frames coincide. With perfectly regular timing this is ambiguous by whole frames; the report gives the residual, anomalies are matched with a 0.15 s tolerance, and nothing is re-attributed if the alignment is not reliable.
  • Authenticity: the log is written by the client. Its SHA-256 and its link to the video's hash are verified, but a modified client could write any log.

Limitations

  • A byte-perfect transfer proves only that the backend holds the same bytes the client had. It cannot prove the original recording has no dropped frames.
  • Frames dropped before encoding, with timestamps re-generated at a constant rate, leave no timestamp gap. Only content cues (motion spikes) hint at them, and those are low confidence.
  • Without a capture log or reference recording, capture drops and encoder drops cannot be told apart; such anomalies are reported with likely cause 'undetermined'. With a browser capture log, see capture_evidence.can_prove / cannot_prove for what it settles.
  • Content checks use fixed thresholds on 160x90 grayscale thumbnails. Static scenes, slow motion, fades and scene cuts can cause misses or false alarms. Thresholds are measured in the M3 test set.
  • Only the first video stream is analysed; audio is ignored.
  • Decoder error messages are mapped to frames via packet timestamps; with B-frames the visibly damaged frame can differ from the reported one, and damage can propagate until the next keyframe.
